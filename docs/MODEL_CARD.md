# Model Card – Hospital Triage ML Classifier

> [!IMPORTANT]
> This model is a **decision-support prototype only**. It is NOT a certified medical device.
> Clinicians make the final triage decision. Never use this model to replace professional clinical judgment.

---

## 1. Purpose

Classify incoming emergency patients into one of **five urgency levels** (ESI-style 1 = most critical → 5 = least urgent) based on vital signs and symptom keywords. The output is used to:

- **Prioritise the waiting queue** (Level 1 patients are seen first)
- **Drive auto-allocation** to the appropriate ward (ICU for Level 1, Emergency for Level 1–2, General for Level 3–5)
- **Trigger clinical alerts** to the assigned doctor and nursing staff
- **Generate SHAP-based reason tags** that explain the prediction to clinicians

---

## 2. Training Data

| Attribute | Detail |
|-----------|--------|
| **Source** | Fully synthetic dataset generated by rule-based ESI heuristics |
| **Size** | Sufficient to train XGBoost to convergence (see metrics below) |
| **Labels** | Assigned by deterministic clinical rules, not by real clinicians |
| **Demographics** | Age and gender distributions based on plausible ED population ranges |

> [!WARNING]
> **This model was NOT trained on real patient data.** No real electronic health records (EHR), hospital charts, or patient identifiers were used. The dataset is designed to demonstrate system functionality, not to reflect real-world clinical distributions.

## 3. Input Features

The model receives the following 16 features (from `ml/model/features.json`):

| Feature | Type | Description |
|---------|------|-------------|
| `age` | numeric | Patient age in years |
| `gender` | binary | 1 = Male, 0 = Female |
| `sbp` | numeric | Systolic blood pressure (mmHg) |
| `dbp` | numeric | Diastolic blood pressure (mmHg) |
| `hr` | numeric | Heart rate (bpm) |
| `spo2` | numeric | Oxygen saturation (%) |
| `temp` | numeric | Body temperature (°C) |
| `rr` | numeric | Respiratory rate (breaths/min) |
| `chest_pain` | binary | Keyword detected in symptoms |
| `breathlessness` | binary | Keyword detected in symptoms |
| `unconscious` | binary | Keyword detected in symptoms |
| `severe_bleeding` | binary | Keyword detected in symptoms |
| `fever` | binary | Keyword detected in symptoms |
| `abdominal_pain` | binary | Keyword detected in symptoms |
| `headache` | binary | Keyword detected in symptoms |
| `minor_injury` | binary | Keyword detected in symptoms |

Keyword extraction uses simple string matching (`in` operator on lowercased symptoms). This is intentionally lightweight; see **Known Limitations**.

## 5. Performance Metrics

All metrics are from **held-out test data** (see `ml/model/metrics.json`):

| Metric | Value |
|--------|-------|
| **Overall accuracy** | **95.75 %** |
| **Recall – Level 1 (Critical)** | **91.88 %** |
| **Recall – Level 2 (Emergent)** | **81.90 %** |
| **Mean critical recall (Levels 1 + 2)** | **86.89 %** |

> [!NOTE]
> Recall for Level 1 is prioritised during training. Missing a critical patient (false negative at Level 1) is a much more dangerous error than over-triaging a mild patient.

## 6. Safety-Override Rules

Even if the ML model returns a lower urgency level, the following hard rules in `ml/predict.py` **override** the prediction and force Level 1:

| Condition | Threshold | Rationale |
|-----------|-----------|-----------|
| SpO₂ (oxygen saturation) | < 85 % | Hypoxia is immediately life-threatening |
| Heart rate | < 40 or > 150 bpm | Extreme brady/tachycardia → cardiac risk |
| Systolic blood pressure | < 75 mmHg | Haemodynamic shock |
| Respiratory rate | < 8 or > 30 breaths/min | Respiratory failure |

**Why these overrides exist:** XGBoost may occasionally mislabel edge cases when rare combinations of vitals appear. These clinically established thresholds act as a safety net, ensuring that any patient in immediate physiological danger is never assigned a low urgency level regardless of model output.

---

## 7. Explainability – SHAP Reason Tags

After prediction, SHAP (SHapley Additive exPlanations) values are computed for the top contributing features using `shap.TreeExplainer`. Features with the highest positive impact on the predicted class are translated into human-readable **reason tags** (e.g., `"Low SpO₂"`, `"Elevated Heart Rate"`, `"Chest Pain"`).

These tags are:
- Displayed on the patient card in the live dashboard
- Stored in the `reason_tags` field of the patient record
- Written to the audit log at intake time

SHAP values are computed per-prediction (not globally) so the explanation is specific to each patient's vitals and symptoms.

## 8. Known Limitations

1. **Synthetic training data** – The model has never seen a real patient. Its performance on real ED populations is unknown and likely lower than these metrics suggest.
2. **No real clinical validation** – The model has not been validated in any clinical setting, IRB study, or prospective trial.
3. **Simple keyword matching** – Symptom features rely on exact substring matching. Misspellings, abbreviations, or free-text clinical notes are not handled.
4. **Fixed feature set** – The model does not use lab results, imaging, medication history, or comorbidities, all of which are standard in real triage tools.
5. **Static model** – There is no online learning. The model does not improve with usage.
6. **English-only** – Symptom keywords are matched in English only.
7. **Binary gender encoding** – Gender is encoded as binary (M/F); this does not reflect clinical or social complexity.

**The final triage decision ALWAYS rests with the attending clinician.** The system's output is advisory only.
